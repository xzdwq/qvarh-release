# Qvarh Release Builder

VS Code расширение для визуальной сборки релизной ветки из локальных git-веток: без подключения к таск-трекеру/Bitbucket API — всё, что нужно, уже есть в `.git`. Ссылки на задачу и PR (опционально, см. "Настройка") собираются по шаблону URL, без единого сетевого запроса к внешним сервисам.

## Что делает

1. Показывает текущую ветку и позволяет явно **Pull** любую конкретную ветку (main или dev — checkout + pull, по вашему выбору) — кнопка, как и "Обновить список веток", показывает текст-индикатор, пока идёт, и не нажимается повторно, пока не закончит. Автоматического checkout/pull при открытии панели нет — переключение веток происходит только по вашей явной команде. Панель открывается сразу по нажатию "Собрать релизную ветку", ещё до завершения этих проверок — список веток показывает лоадер, пока грузится.
2. Показывает список веток репозитория (локальных и remote-tracking, в панели с изменяемой высотой — тянется за нижний край, как textarea, только по вертикали), отсортированный по дате последнего коммита (сначала свежие), с фильтром по названию — через пробел можно ввести несколько терминов сразу (`PROJ-123 PROJ-456`), найдутся ветки, подходящие под любой из них. По умолчанию remote-tracking ветка не показывается отдельной строкой, если для неё есть локальная пара с тем же именем (иначе почти каждая ветка дублировалась бы в списке дважды) — настраивается (`qvarhRelease.git.hideDuplicateRemoteBranches`, см. "Настройка"). Рядом с фильтром — флажок "Скрыть ветки, уже полностью в main" и поле "Показывать веток" (принимает только цифры); оба применяются ОДНИМ действием — кнопкой "Применить" (показывает "Применяем…", пока список пересобирается): флажок не действует мгновенно сам по себе, потому что скрытие происходит на сервере ДО среза по лимиту — иначе "показывать 2000" при включённом скрытии показало бы меньше 2000 строк (часть уже отобранных вырезалась бы фильтром постфактум). Отдельным, независимым флажком — "Скрыть служебные ветки" (qa, revert-pr-*, chore/* и т.п. — см. "Префиксы служебных веток" в настройках): в отличие от "уже в main", это просто проверка префикса имени без единого git-вызова, поэтому применяется сразу при переключении, без кнопки "Применить". Единственное место, где настраивается лимит показа — см. "Настройка". У каждой ветки видно дату/автора/тему последнего коммита, а по кнопке "показать коммиты" — полный список её коммитов относительно основной ветки (sha, дата, автор, тема; если ветка заведена не от dev, а от другой опорной ветки — см. раздел ниже — отдельной строкой указано, от какой именно). Рядом — кликабельные ссылки на задачу в таск-трекере (по ключу вида `PROJ-123` в имени ветки) и, если ветка уже мержилась в dev, на PR и коммит в Bitbucket (см. раздел "Настройка").
3. Вы отмечаете чекбоксами, какие ветки идут в релиз — рядом виден список уже выбранных.
4. По кнопке "Построить хронологию" (без указания даты — она пока не нужна) берёт коммиты, уникальные относительно dev-ветки (`git merge-base` + `git log --first-parent`), и строит единую хронологию — все коммиты всех выбранных веток, отсортированные по реальному времени коммита. Слева от списка — компактная "дорожка" (без сторонних библиотек — один SVG, нарисованный поверх уже отрендеренного списка по его реальным координатам, поэтому не ломается от переноса длинной темы коммита на несколько строк): вертикальный ствол dev, и по одной цветной дорожке на каждую выбранную ветку, ответвляющейся от ствола плавной кривой в точке её первого коммита и точно так же сливающейся обратно, если ветка уже мержилась — тем же авторитетным git-запросом, которым и так считается номер PR для бейджей (`GitService.listMergeEvents` — merge-коммиты first-parent истории dev с subject'ом вида `Merged in <ветка> (pull request #N)`), а не подсматриванием субъектов уже загруженных для показа контекстных коммитов dev (те не гарантированно содержат нужный коммит — окно дат, лимит, свёрнутый список — из-за чего влитые ветки могли выглядеть как ещё не влитые); строка слияния поэтому видна на дорожке всегда, даже при свёрнутых контекстных коммитах. Точка слияния на самом стволе при этом красится в цвет ветки — видно, где именно она влилась. Если ветку за её жизнь мержили НЕСКОЛЬКО раз (часть коммитов отдельным PR раньше, часть — позже; так тоже бывает), на дорожке отмечена ТОЧКА под каждое такое слияние, а не только под последнее — дорожка при этом закрывается (перестаёт быть нарисованной) только на самом свежем слиянии, все более ранние — просто отметки по пути. Если слияние не нашлось — дорожка обрывается пунктирным "хвостом" за нижний (или, если не нашлось начало ветвления в показанном окне — за верхний) край видимой хронологии — сигнал "здесь неизвестность", а не оборванная линия. Цвет каждой ветки — по порядку первого появления в списке (а не хэш от имени), с шагом в 137.5° по кругу HSL — так соседние по времени ветки почти всегда получают максимально разные, а не случайно похожие оттенки. Сразу следом за построением хронологии, автоматически (отдельной кнопки для этого больше нет), реально прогоняет cherry-pick во временном git worktree (не трогая ваш рабочий каталог), чтобы точно, а не эвристически, показать, на каком коммите будет конфликт — доступно ещё до создания релизной ветки. На каждый конфликтующий файл расширение показывает РЕАЛЬНЫЙ источник — не догадку по пересечению файлов, а фактически последний коммит, менявший этот файл в состоянии worktree непосредственно перед конфликтом (`git log -1 -- файл` в момент конфликта, пока HEAD ещё не откачен): sha, тема, автор, дата и ссылка на коммит в Bitbucket, а если sha совпадает с одним из показанных коммитов хронологии — ещё и имя ветки. Работает одинаково надёжно и когда причина — другая выбранная ветка, и когда причина — уже смёржённая в main более ранняя версия ЭТОЙ ЖЕ задачи. Мелким серым — "контекстные" коммиты dev-ветки за тот же период (что ещё происходило параллельно, для общей картины, не для cherry-pick), тоже со ссылками на таск-трекер/Bitbucket, плюс ещё один такой же серый пункт ПЕРЕД самым первым коммитом хронологии — последний коммит dev строго до её начала, чтобы сразу было видно, откуда всё начинается; всё это можно свернуть одной кнопкой, если их много. Весь блок хронологии тоже можно свернуть целиком (стрелка у заголовка), а кнопка "Очистить" рядом с "Построить хронологию" сбрасывает и её, и выбор веток — начать заново, не закрывая панель. Сразу после построения хронологии, не блокируя её показ (с индикатором загрузки, пока идёт), автоматически запускается ещё один, отдельный поиск: ветки, которые отсоединились от dev раньше самой ранней ветки в текущей хронологии и всё ещё НЕ СЛИТЫ В САМУ DEV (не в main — ветка, уже влитая в dev, но ждущая своего релиза, это норма, а не забытая задача) — подсказка "возможно, где-то есть забытая, давно не трогаемая задача, которую вы просто не выбрали".
5. Внизу хронологии — готовая команда `git cherry-pick` для тех, кто предпочитает провести (или дособрать) релиз вручную, а не через кнопки шага 9: перечисляет ещё не применённые отмеченные коммиты в порядке хронологии, каждый sha — цветной "чип" в цвет своей ветки (тот же цвет, что и в дорожке слева), кликабельный (ссылка на коммит в Bitbucket) и с подсказкой при наведении — именем ветки. Если среди коммитов есть конфликтные (по dry-run — см. шаг 7), команда разбивается НА НЕСКОЛЬКО: конфликтный коммит — последний в своей команде (залит цветом конфликта, но с обводкой в цвет своей ветки — чтобы не терять связь с веткой), следующая команда начинается со следующего коммита, чтобы после разрешения конфликта в редакторе было однозначно понятно, какую команду брать дальше. У каждой команды — кнопка "Копировать" (весь текст, с полными sha, а не сокращёнными); скопированная команда становится блёклой, чтобы не запутаться, что уже брали, — состояние сбрасывается кнопкой "Сбросить состояние копирования" или при построении новой хронологии.
6. Подсвечивает коммиты, которые правят те же файлы, что и коммиты с других выбранных веток (потенциальный порядок/конфликт, бейдж показывает конкретные имена веток-пересечений, а не просто число), и отдельным бейджем — коммиты/ветки, чьё содержимое уже есть в основной ветке (по patch-id — см. ниже), обычно не нуждаются в повторном cherry-pick. Для ветки (в списке веток, не в хронологии) бейдж трёхзначный: "уже в main" (все коммиты ветки уже там), "частично в main" (только часть — например, задачу довыполняли уже после того, как первую половину отпустили отдельным релизом) или отсутствие бейджа (ничего ещё не выпущено). Точный расчёт "частично" требует списка всех коммитов ветки — до разворачивания ("показать коммиты") расширение показывает только дешёвое приближение по последнему коммиту ("уже в main" или ничего), а "частично" проявляется сразу после разворачивания, когда точные данные по каждому коммиту уже загружены.
7. Если dry-run (шаг 4) находит настоящий конфликт (не "уже применено"), под конфликтующим коммитом появляется подсказка о вероятной причине. Если сам конфликтующий коммит уже отмечен бейджем "уже в main" — предлагается просто исключить его из релиза (сняв галочку), а не разрешать конфликт: скорее всего, это просто старая задача, попавшая в main отдельно от текущего релиза. Иначе расширение ищет по ВСЕМ веткам репозитория коммиты, которые тоже меняют именно конфликтующий файл и ещё не выпущены в main (узкий, дешёвый запрос — `git log --all --not <mainRef> -- файл`, а не сканирование сотен веток целиком, как раньше делал общий поиск "возможных зависимостей", убранный из расширения — он оказался слишком шумным: находил любое пересечение по файлу, даже правку годичной давности по не связанной причине). Если такие коммиты находятся — показывает до 5 самых свежих (ветка, коммит, тема, дата, ссылка) с мыслью "возможно, дело не в противоречащих правках, а в забытой задаче — добавьте её в хронологию раньше"; если нет — прямо говорит, что причину найти не удалось и конфликт, похоже, придётся разрешать вручную.
8. Когда всё устраивает — вводите дату релиза (предзаполнена сегодняшней) и нажимаете "Создать релизную ветку": только на этом шаге она реально создаётся от основной ветки.
9. Собирает план в релизную ветку автоматически (до первого конфликта) или пошагово вручную, с возможностью снять галочку с любого коммита.

## Ограничения текущей версии

- Поиск вероятной причины конфликта (шаг 7) — эвристика по конкретному конфликтующему файлу, не по семантике кода: находит ветки, которые тоже его меняют и ещё не выпущены, но не может гарантировать, что содержимое действительно связано с конфликтом (просто высокая вероятность, до 5 самых свежих кандидатов, дата коммита показывается явно — можно судить самостоятельно). Ограничено 50 кандидатами (сортировка по свежести — самые старые могут быть отброшены обрезкой `git log`, не хуже, поскольку они и так наименее вероятная причина).
- Определение "уже в main" — по **patch-id** (подпись содержимого диффа) как основному сигналу, а не по SHA/ancestry: задача обычно попадает в main не напрямую, а через cherry-pick в релизную ветку, который создаёт новый коммит с другим SHA. Это надёжно ловит и прямые коммиты, и чистый cherry-pick (в т.ч. если несколько коммитов при сборке релиза склеили в один — проверяется дополнительно вся ветка целиком как один дифф). Есть и второй, дополнительный сигнал — **subject + дата автора** (`GitService.buildMainSubjectDateIndex`): patch-id хэширует диф ЦЕЛИКОМ, включая неизменённые строки-контекст вокруг правки, и перестаёт совпадать, если эти соседние строки успели разъехаться из-за ДРУГИХ, не связанных с этим коммитом правок — а cherry-pick/rebase дату автора оригинала гарантированно не трогает, так что пара (subject, authorDate) остаётся надёжным отпечатком даже тогда, когда patch-id уже не совпадает (подтверждено на реальном примере с "разъехавшимся" соседним комментарием в файле). Ветки/имена релизных и служебных веток (шаблон релизной ветки + настраиваемые префиксы) исключаются из кандидатов в причину конфликта по имени, а не по ancestry — это структурно надёжнее.

  Важная деталь реализации: индекс patch-id для основной ветки строится по **полной** истории (`git log -p`, без `--first-parent`), а не только по first-parent цепочке main. Реальное содержимое задачи попадает в main как ВТОРОЙ родитель merge-коммита (сама задача была на релизной ветке) — first-parent-обход main видел бы только сам merge-коммит и коммиты, сделанные непосредственно на main, и пропускал бы диффы коммитов внутри смёрженных веток. Это отдельная логика от множества first-parent SHA dev-ветки (`buildDevFirstParentSet`, см. следующий раздел), которое, наоборот, строится строго по first-parent — там задача другая (найти точку ветвления, а не сравнить содержимое).

  Статус ветки в списке (не хронологии) — "уже в main"/"частично"/ничего — сначала (мгновенно) показывается ДЁШЕВОЕ приближение по patch-id последнего коммита (один пакетный git-вызов на весь показанный список веток разом): если последний коммит совпал — "уже в main", если нет — бейдж пока не показывается. Сразу следом, в фоне, не блокируя список, досчитывается ТОЧНЫЙ статус по patch-id КАЖДОГО коммита каждой показанной ветки — тогда и проявляется "частично" (часть коммитов ветки уже в main, часть ещё нет). Это дороже (до двух git-вызовов на ветку вместо одного пакетного на весь список), поэтому и вынесено в отдельный, следующий шагом проход, а не встроено в первый рендер списка.
- Dry-run (запускается автоматически, см. шаг 4) проверяет только сам cherry-pick (быстро останавливается на первом конфликте); дальнейшие коммиты после первого конфликта остаются непроверенными до повторного запуска. Отдельно обрабатывается "пустой" cherry-pick (`git` пишет "The previous cherry-pick is now empty" — содержимое уже полностью в целевой ветке): git в этом случае тоже завершается ненулевым кодом, но БЕЗ единого конфликтующего файла в `git status` — раньше это ошибочно показывалось как "конфликт (0 файлов)" (сбивающее с толку сообщение без единого файла для разрешения), теперь распознаётся отдельно и не считается конфликтом. При реальном (не dry-run) применении плана такой пункт тоже просто пропускается (`git cherry-pick --skip`) как уже применённый, а не превращается в подвисший cherry-pick без единого реального конфликта для разрешения.
- Команда для ручного cherry-pick (шаг 5) разбивается на несколько только на "conflict" (по dry-run); "пустой" cherry-pick (см. выше) отдельно не выделяется и команду не разбивает — реальный `git cherry-pick` в этом случае тоже остановится с сообщением "The previous cherry-pick is now empty", и это нужно будет разрешить самостоятельно (`--skip`/`--allow-empty`), как при обычном ручном cherry-pick. Состояние "скопировано" — только визуальная пометка на стороне панели (какие команды вы уже брали), она не хранится между перезапусками VS Code и не влияет на то, что реально применено в git.
- Дорожка веток (шаг 4) сознательно НЕ показывает весь репозиторий (в отличие от, например, vscode-git-graph) — только ствол dev и явно отмеченные ветки в пределах уже построенной хронологии, поэтому не подходит для общего просмотра истории репозитория, только для наглядности при подготовке конкретного релиза. Обнаружение слияния ветки обратно в dev — по subject merge-коммита first-parent истории dev (`GitService.listMergeEvents`, `--merges`, subject вида `Merged in <ветка> (pull request #N)`); если PR смёржен со "squash" (одним обычным коммитом, а не merge-коммитом с двумя родителями) или без стандартного сообщения Bitbucket, слияние не будет распознано, и дорожка ветки останется нарисованной как "ещё не влита", даже если по факту она уже влита.
- Автопоиск более старых невлитых веток (см. шаг 4) — тоже эвристика, а не гарантия: широкий скан `git log --all --not <devRef> --no-merges`, кандидаты фильтруются по patch-id/subject+дата так же, как и статус "уже в main" (только относительно dev, а не main), ограничен 100 кандидатами и 10 показанными ветками (сортировка по свежести) — на очень старых и активных репозиториях часть кандидатов может быть отброшена. `--no-merges` исключает чисто технические merge-коммиты (вида "Merge branch 'dev' into feature/X" — кто-то подтягивал dev в свою ветку) — у них нет своего осмысленного диффа, и без этого исключения они ложно оставались "невлитыми" даже когда реальное содержимое ветки уже давно в dev.
- Merge-конфликты при реальном cherry-pick разрешаются вручную в редакторе; расширение только останавливается и ждёт.
- OAuth/API-интеграция с таск-трекером/Bitbucket сознательно не используется — все данные берутся из локального git. Ссылки на задачу/PR/коммит (см. "Настройка") — это просто URL, собранные по шаблону из ключа задачи в имени ветки и номера PR, распарсенного из subject merge-коммита (`Merged in feature/PROJ-123 (pull request #42)`) — без единого обращения к API таск-трекера или Bitbucket. Если ветка ещё не мержилась в dev, номера PR и ссылки на него нет — это ожидаемо, а не ошибка.
- Выбор коммитов из ветки на этапе картотеки веток — только просмотр (read-only); исключить отдельные коммиты можно после построения хронологии, в списке ниже.
- Список веток по умолчанию показывает только N самых свежих (см. `qvarhRelease.git.branchListLimit`, по умолчанию 100; меняется полем "Показывать веток" прямо в панели сборки релиза) — это защита от зависания интерфейса при большом числе веток в репозитории. Поиск по фильтру ищет по всем веткам, но тоже ограничен тем же числом совпадений.
- Если у выбранной ветки нет общей истории с dev-веткой (например, ветка из другого проекта или после history rewrite), она пропускается с понятной причиной в блоке ошибок — остальные выбранные ветки при этом строятся нормально.
- На каждую ветку берётся не более 300 коммитов относительно dev-ветки (защита от аномально большого диапазона, например если dev сильно отстал или настройка `devBranch` указывает не туда) — при превышении показаны только самые свежие, с явным предупреждением. Диффы файлов по коммитам считаются параллельно (до 12 одновременно), а не по одному — иначе даже несколько сотен коммитов могли ощущаться как зависание.
- Любая git-команда, которая не отвечает (например, зависла на вводе учётных данных в неинтерактивном контексте), принудительно прерывается с понятной ошибкой — расширение не должно зависать бесконечно. Порог — 2 минуты (изначально было 25 секунд: этого хватало для защиты от реально зависшего процесса, но оказалось МАЛО для некоторых легитимно медленных операций — например, "показать коммиты" на релизной ветке, где просмотр статуса "в main" может пройти по большому куску истории main, если у релизной ветки очень старые исходные даты авторов cherry-pick'нутых коммитов; раньше это ошибочно завершалось как "block timeout reached", хотя git продолжал реально работать).
- Проверка patch-id по списку конкретных коммитов (используется и в быстром, и в фоновом уточнении статуса "в main") бьёт список SHA на пачки по 200 и запускает несколько git-процессов вместо одного — на Windows суммарная длина аргументов процесса ограничена, и при большом лимите показа веток (сотни-тысячи) один вызов на всё сразу мог упереться в этот лимит (`spawn ENAMETOOLONG`). Сам по себе большой лимит (сотни-тысячи веток) не падает, но фоновое уточнение "частично/полностью в main" на таком масштабе может занимать заметное время (в теории — минуты на тысяче веток) — это не блокирует список (он показан сразу с быстрым приближением), просто точные бейджи проявляются постепенно.
- Блок ошибок можно закрыть вручную (крестик) до появления следующей — раньше он либо не показывался повторно с тем же текстом, либо оставался висеть, пока его не сменит новая ошибка.
- Ссылки на основную/dev-ветку, индекс "ветка → номер PR" и множество first-parent SHA dev-ветки кэшируются один раз на весь период между обновлениями списка веток (Pull/явный "Обновить список веток" сбрасывают кэш) — раньше всё это пересчитывалось заново на каждое изменение фильтра/лимита, включая фоновое уточнение статуса "в main", из-за чего на репозитории с активной dev-веткой фильтрация и построение хронологии заметно тормозили. Сама фильтрация/срез по лимиту также защищены от гонки устаревших запросов: если, пока считался предыдущий (более медленный) результат, пользователь успел ввести в фильтр что-то новое, устаревший результат просто не отправляется в панель — раньше он мог прийти ПОЗЖЕ нового и молча его перезаписать (выглядело как "поиск находит нужное, а потом добавляет ещё лишнее" и "не поспевает за вводом").
- Фоновое уточнение статуса "в main" (см. выше) идёт в режиме single-flight — если запустился новый проход (например, от очередного нажатия клавиши в фильтре), пока предыдущий ещё не закончился, они не выполняются параллельно: новый запрос ждёт своей очереди, а устаревшие промежуточные — просто отбрасываются (учитывается только самый свежий). Без этого частый ввод в фильтре на репозитории с сотнями-тысячами веток мог бы запускать десятки одновременных многоминутных сканов, забивающих пул git-процессов настолько, что даже лёгкие операции вроде "показать коммиты" одной ветки заметно подвисали бы в ожидании ресурсов.
- Все ФОНОВЫЕ операции (уточнение статуса "в main" по списку веток) гонят не более 6 git-процессов параллельно вместо 12 — спавн процесса на Windows заметно дорогая операция (антивирус, создание процесса), и 12 параллельных запусков, сустейненных минутами на большом масштабе, ощутимо конкурируют за ресурсы ОС с любым другим созданием процессов на компьютере — например, с открытием ссылки во внешнем браузере (тоже запуск процесса), из-за чего оно могло заметно подвисать на фоне такого скана. Интерактивные операции, результата которых пользователь ждёт немедленно (например, диффы файлов при построении хронологии по уже выбранным веткам), по-прежнему используют более высокую конкурентность — там счёт обычно идёт на единицы веток, а не на сотни.
- Если "показать коммиты" запрошено для ветки, которой уже не оказалось в актуальном списке (редкая гонка с одновременным обновлением списка веток) — расширение явно сообщает об этом, а не оставляет кнопку в состоянии "Загрузка…" навсегда.

## Если что-то пошло не так (например, не переключается ветка через интерфейс VS Code)

Обычно это значит, что где-то остался незавершённый `cherry-pick` (конфликт, который не разрешили и не отменили) — VS Code блокирует переключение веток, пока в репозитории есть незакоммиченный/конфликтующий cherry-pick. Расширение теперь:

- при каждом открытии панели проверяет, нет ли незавершённого cherry-pick, и явно предупреждает об этом вверху панели;
- на всякий случай подчищает "осиротевшие" временные worktree от dry-run (`git worktree prune`), если сессия была прервана (например, закрытием VS Code) до завершения проверки конфликтов;
- добавляет кнопку **Отменить сборку (cherry-pick --abort)** рядом с кнопками разрешения конфликта — если хотите просто выйти из текущей попытки, а не разрешать конфликт.

Если кнопка не помогла, то же самое можно сделать вручную в терминале: `git cherry-pick --abort`, при необходимости `git worktree list` + `git worktree prune`.

## Если ветка показывает слишком много "чужих" коммитов

Если feature/fix-ветки у вас создаются от `dev`, а не от основной ветки (`main`), а `dev` заметно ушёл вперёд — считать коммиты ветки относительно `main` неверно: в список попадёт вся история `dev` между ней и `main`, а не только собственные коммиты ветки. Расширение считает коммиты ветки относительно **dev-ветки** (`qvarhRelease.git.devBranch`, по умолчанию `dev`), а не основной. Основная ветка используется только для создания самой релизной ветки и для dry-run. Если у вас ветки создаются прямо от main, укажите в `devBranch` то же значение, что и в `mainBranch`.

Отдельный случай: если ветку уже смёржили в dev, обычный `git merge-base(dev, ветка)` совпадает с самим кончиком ветки — "своих" коммитов формально не остаётся, хотя ветка явно содержит свою работу. Причём так бывает не только один раз: одно и то же имя ветки может заводиться от dev, дорабатываться и вливаться заново несколько раз подряд (задачу довыполняли уже после того, как первую часть отпустили отдельным PR) — тогда часть работы ветки лежит "внутри" dev с очень давних пор.

Расширение это учитывает: идёт по собственной first-parent истории ветки от кончика назад и останавливается, только дойдя до коммита, который сам уже часть first-parent истории dev — то есть до настоящей самой ранней точки ветвления, независимо от того, сколько раз ветку успели влить и завести заново. Попутно исключаются чистые merge-коммиты внутри собственной истории ветки (например, "Merge branch 'dev' into feature/PROJ-123" — синхронизация с dev внутри своей же ветки) — это административные действия, а не реальная работа, включать их в cherry-pick не нужно.

Технически множество first-parent SHA dev-ветки строится один раз одним git-вызовом (без диффов, поэтому дёшево даже на многотысячной истории) и переиспользуется для всех проверяемых веток — иначе на сотнях веток счёт шёл бы на минуты. Более ранний вариант этого механизма (пошаговый peel-back через повторные `git merge-base` с индексом "чей коммит куда влился") мог терять коммиты САМЫХ РАННИХ раундов, если между раундами реиспользования ветки в dev успевали влиться другие, никак не связанные задачи — прямой обход собственной истории ветки этой проблеме не подвержен.

Отдельный случай — служебные ветки вроде `revert-pr-*`, которые Bitbucket заводит не от dev, а от ТЕКУЩЕЙ ветки, на которой сделали revert (обычно это ветка вида `qa` — см. "Префиксы служебных веток" в настройках). Если считать её собственные коммиты только относительно dev, `merge-base(dev, ветка)` может оказаться очень старой точкой (там, где dev и qa в последний раз расходились) — и в "свои" ошибочно попадёт вся история qa за этот период, а не единственный реальный коммит revert'а. Расширение проверяет ВСЕ точное (не префиксное) совпадение с nonTaskBranchPrefixes, реально существующее в репозитории (обычно только `qa`), как дополнительную опорную ветку и берёт ближайшую к кончику ветки точку слияния — для обычных ветках от dev ничего не меняется, а для revert-веток от qa коммиты считаются верно, и панель дополнительно показывает, от какой ветки реально была заведена такая ветка.

## Настройка

Всё настраивается в боковой панели (иконка на Activity Bar), без правки settings.json — панель работает только с профилями проектов, единого конфига "по умолчанию" больше нет. Исключение — лимит показа веток ("Показывать веток"): он живёт только в самой панели сборки релиза (рядом с фильтром веток), чтобы не дублировать одну и ту же настройку в двух местах.

Блок **"Проекты"** — отдельные, независимо сохранённые профили настроек, один на репозиторий: имя, обязательный путь к репозиторию (workspace на который можно откатиться, как раньше, здесь нет — путь всегда указывается явно) и:

- **Основная ветка** — от неё создаётся релизная ветка, и от неё считается dry-run.
- **Dev-ветка** — от неё вычисляется, какие коммиты в feature/fix-ветке "свои" (`git merge-base` с dev, а не с main — см. раздел выше).
- **Remote** — имя git remote (обычно `origin`), список веток строится из `refs/heads` и `refs/remotes/<remote>`.
- **Шаблон релизной ветки** — например `release/release-{date}`. Ветки в неймспейсе до первого `/` (т.е. всё, что начинается с `release/`) считаются релизными и не участвуют в поиске вероятной причины конфликта, независимо от даты/суффикса.
- **Префиксы служебных веток** — через запятую (по умолчанию `qa, revert-pr-, chore/`) — ещё не задачи, тоже исключаются из поиска вероятной причины конфликта. Точное совпадение из этого списка (не префикс — обычно это `qa`) также используется как дополнительная опорная ветка при подсчёте "своих" коммитов — см. раздел выше про revert-ветки.
- **Скрывать remote-ветку, если есть локальная с тем же именем** (галочка, по умолчанию включена) — большинство веток и так существуют одновременно как локальная и как remote-tracking ссылка с тем же коммитом; без этой галочки они показывались бы в списке дважды подряд. Локальная версия остаётся в списке как основная — типичный сценарий работы: сначала Pull (checkout + pull), дальше работа идёт с локальной веткой.
- **Базовый URL задачи в таск-трекере** (по умолчанию пусто — ссылки не показываются, пока не задано) — ключ задачи (напр. `PROJ-123`) ищется в имени ветки (`feature/PROJ-123`) или, если там не нашёлся, в subject коммита, и добавляется через `/`. Подходит для Jira (`https://your-company.atlassian.net/browse`) и для любого другого трекера с таким же принципом адресации "базовый URL + ключ задачи".
- **Bitbucket workspace** и **Bitbucket repo slug** (если пусто — берётся имя папки репозитория) — используются для ссылок на PR и коммит.

Хранятся одним списком в `qvarhRelease.projects` — можно держать конфиг сразу нескольких репозиториев и запускать сборку для любого из них, не переключая открытый в VS Code workspace.

У каждого сохранённого проекта в списке — три кнопки: 🚀 сразу открывает панель сборки релиза ДЛЯ ЭТОГО проекта (со своими настройками, не трогая открытый workspace), ✎ подгружает его значения в форму для редактирования, ✕ удаляет профиль (после подтверждения прямо в списке — удаляются только сохранённые настройки, сам репозиторий на диске не трогается). Кнопка **"+ Добавить проект"** открывает пустую форму для нового.

Продолжить прерванную сборку (после перезапуска VS Code или конфликта) можно командой `Qvarh Release: продолжить сборку релиза` из палитры команд (Ctrl+Shift+P) — отдельной кнопки в боковой панели для этого нет. Команда работает только с ТЕКУЩИМ открытым workspace, а не с произвольным профилем проекта — прогресс сборки хранится в workspace state VS Code, который привязан к конкретной открытой папке. Если вы начали сборку для проекта через 🚀, не открывая его как workspace, и прервали её, продолжить её получится только открыв этот репозиторий как workspace явно.

## Использование

1. Добавьте проект в боковой панели ("+ Добавить проект") с путём к репозиторию — или откройте в VS Code workspace с нужным git-репозиторием и запустите сборку через команду `Qvarh Release: собрать релизную ветку` из палитры команд (Ctrl+Shift+P).
2. Нажмите 🚀 у нужного проекта — откроется панель сборки в редакторе. Она ничего не переключает и не пуллит автоматически — только показывает текущую ветку и список веток репозитория.
3. При необходимости нажмите **Pull** конкретной ветки (main или dev — введите имя, есть автоподсказка).
4. Отфильтруйте и отметьте чекбоксами нужные ветки (списком видно, что уже выбрано; по кнопке "показать коммиты" можно посмотреть коммиты ветки заранее) → **Построить хронологию выбранных веток**. Сразу следом автоматически прогоняется проверка на конфликты — отдельной кнопки для этого нет; кнопка **Очистить** рядом сбрасывает и хронологию, и выбор веток, если нужно начать заново.
5. Расширение покажет единый список коммитов всех отмеченных веток, отсортированный по времени, с цветной меткой ветки у каждого коммита, плюс мелкие серые строки — "контекстные" коммиты dev-ветки за тот же период (кнопка над списком скрывает их, если их много). Убедитесь, что в рабочем каталоге нет незакоммиченных изменений — они понадобятся чистыми на шаге создания ветки (8).
6. Посмотрите на бейджи: "пересекается с N коммит(ами) на других ветках", "уже в main" (значит, содержимое коммита уже есть в основной ветке — обычно не нуждается в повторном cherry-pick), и результат автоматической проверки на конфликты — "конфликтов нет", "конфликт: <файлы>" (с реальным источником на каждый файл) или "уже применено (пустой cherry-pick)" — это отдельный, третий случай: содержимое коммита УЖЕ полностью есть в основной ветке, и git сам подтверждает это при попытке cherry-pick (а не наша эвристика по patch-id/subject+date). Остановка происходит на первом настоящем конфликте; если сняли галочку с проблемного коммита, проверка не перезапускается сама — постройте хронологию ещё раз (кнопкой выше), если нужен свежий прогон.
7. Если возник настоящий конфликт (не "уже применено") — под ним появится подсказка: "уже в main" у самого коммита означает, что его, скорее всего, можно просто исключить из релиза; иначе расширение покажет до 5 других веток, которые тоже меняют конфликтующий файл и ещё не выпущены — вероятно, одну из них и забыли добавить в хронологию раньше.
8. Когда всё устраивает — проверьте дату релиза (предзаполнена сегодняшней, можно поменять) и нажмите **Создать релизную ветку**. Только на этом шаге расширение реально создаёт (или переиспользует) ветку от основной.
9. Выберите режим и запустите настоящую сборку:
    - **Авто** — применяет весь план по порядку, останавливается на первом конфликте.
    - **Пошагово вручную** — по одному коммиту за раз кнопкой "Следующий шаг".
10. Если возник конфликт — разрешите его в файлах как обычно при `git cherry-pick`, затем нажмите **Продолжить после конфликта** (или **Пропустить конфликтующий пункт**).
11. Если закрыли VS Code посреди сборки — команда `Qvarh Release: продолжить сборку релиза` из палитры команд (Ctrl+Shift+P) восстановит план и прогресс для текущего открытого workspace.

## Установка себе в VS Code

### Вариант A — режим разработки (F5), без сборки .vsix

1. Открыть папку проекта расширения в VS Code.
2. Нажать `F5` (или Run → Start Debugging). Откроется второе окно VS Code ("Extension Development Host") с уже загруженным расширением.
3. В этом окне открыть свой рабочий репозиторий и пользоваться командами Qvarh Release.
4. Минус: расширение живёт только пока открыто это окно; после изменений в коде нужно `Ctrl+Shift+F5` (Reload) или пересобрать (`npm run watch` в фоне сам пересоберёт `dist/extension.js`, но окно всё равно надо перезагрузить).

### Вариант B — установка как обычного расширения (.vsix), сохраняется насовсем

1. В терминале в папке проекта:
   ```
   npm run package
   ```
   Это соберёт `dist/extension.js` в production-режиме и создаст файл `qvarh-release-0.1.0.vsix`.
2. В VS Code: `Ctrl+Shift+P` → **Extensions: Install from VSIX...** → выбрать этот файл.

   Либо из терминала:
   ```
   code --install-extension qvarh-release-0.1.0.vsix
   ```
3. Расширение появится в списке установленных (Extensions → значок "..." → Installed), команды — через `Ctrl+Shift+P`, набрать "Qvarh Release".
4. Чтобы обновить после изменений в коде — повторить `npm run package` и переустановить VSIX (VS Code сам предложит обновить/переустановить при том же имени).
